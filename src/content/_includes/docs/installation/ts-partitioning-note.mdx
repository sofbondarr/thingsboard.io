import { Aside } from '@astrojs/starlight/components';

<Aside type="caution" title="Do not use INDEFINITE time-series partitioning in production">
  <p>Time-series data is written into time-based partitions, and on PostgreSQL expired data is normally removed by dropping whole partitions. With <code>INDEFINITE</code> there is only one partition, so cleanup falls back to row-by-row deletes across a single table that keeps growing. The table bloats with dead tuples, the disk space is not returned to the operating system without <code>VACUUM FULL</code>, and reads slow down as it grows.</p>
  {!props.postgresOnly && (
    <p>On Cassandra, expired data is removed by native per-row TTL rather than by dropping partitions, so it still expires on schedule. The cost is different: <code>INDEFINITE</code> puts the whole history of every entity and key into one unbounded wide partition, which degrades reads and compaction as it grows.</p>
  )}
  <p>Keep the default <code>MONTHS</code>, or pick the granularity that matches your write volume — <code>DAYS</code> for high-throughput deployments, <code>YEARS</code> for very low ones. The setting is <code>SQL&#95;POSTGRES&#95;TS&#95;KV&#95;PARTITIONING</code> for PostgreSQL{!props.postgresOnly && (<> and <code>TS&#95;KV&#95;PARTITIONING</code> for Cassandra</>)}.</p>
  <p>Choose this before going to production. Data that has already been written stays in the layout it was written with, so changing the value later does not repartition it.</p>
  {!props.postgresOnly && (
    <p>On Cassandra the consequence is sharper, so decide before the first write. Rows stored under <code>INDEFINITE</code> all go into one partition that is never registered in the partitions table, and once the setting is changed, queries look up the partitions to read and no longer find them. The rows remain on disk and the latest value of each key still resolves, but the history written before the change can no longer be read through the UI or the API.</p>
  )}
</Aside>
